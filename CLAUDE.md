# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SLOPP is an XAMPP port: the stock servers (Apache httpd + PHP, MariaDB, phpMyAdmin or Adminer, and Mailpit for mail) driven by a Rust control panel on GPUI via `gpui-kit` 0.7.1. Modules are deliberately limited to Apache, MySQL and Mailpit (no Tomcat or FTP). Linux, macOS and Windows (new) are supported; keep cross-platform seams (`cfg(unix)`/`cfg(windows)`) intact.

## Commands

On Linux everything runs inside the Nix dev shell (`rustc` is not on the system PATH; GPUI needs the shell's Vulkan/Wayland libraries; the shell also puts Apache, PHP, MariaDB and Mailpit on PATH):

```sh
nix develop -c cargo build -p slopp
nix develop -c cargo run -p slopp
nix develop -c cargo test --workspace
nix develop -c cargo clippy --workspace --all-targets
nix develop -c cargo fmt --all
CARGO_TARGET_DIR=target/core nix develop -c cargo test -p slopp-core    # core only, doesn't wait on the GPUI build lock
nix develop -c cargo test -p slopp-core --test servers -- --ignored       # starts the real servers; as a regular user, not root
nix build                                                               # result/bin/slopp and sloppctl, wrapped with the servers on PATH
```

- The first GPUI build takes ~10 minutes.
- The flake builds with crane: the dependencies are their own derivation, keyed on the manifests and `Cargo.lock`, so after a code-only change `nix build`/`nix run` recompiles just the workspace crates. For iterating, `cargo run` in the dev shell is still quicker (incremental, debug).
- macOS has no Nix shell (the flake is Linux only): use plain `cargo` with Homebrew's `rust`, and `brew install php mariadb` (or keg-only `mariadb@11.8` beside Homebrew's `mysql`; `httpd` is optional, macOS ships one). `scripts/bundle-macos.sh` builds `target/release/SLOPP.app`, with `--dmg` also the disk image.
- Packaging: `scripts/bundle-linux.sh` builds the AppImage outside Nix (plain cargo plus GPUI's apt build deps, as in the workflow; it downloads linuxdeploy and appimagetool into `target/appimage-tools` and runs them with `APPIMAGE_EXTRACT_AND_RUN=1`). `crates/slopp/assets/linux/AppRun` runs `sloppctl` when started under that name. The Windows installer is `crates/slopp/assets/windows/slopp.iss` (`iscc` it after a release build; never change its `AppId`). `scripts/icons.sh` regenerates `slopp.ico` and the X11 PNG from the SVG (`nix shell nixpkgs#librsvg -c scripts/icons.sh`); commit the results.
- Install scripts: `site/install.sh` (Linux, macOS) and `site/install.ps1` (Windows; Windows PowerShell 5.1 too, ASCII only, everything inside one function so `irm | iex` leaks no settings and never `exit`s the user's window) install the latest release, checked against the `digest` GitHub's API lists for each asset, then leave the servers to `sloppctl install-servers`. Both read `sloppctl paths` (`<name>  not found` lines, `Stack root`, `Settings`), so keep that output's labels stable. `--uninstall`/`-Uninstall` runs `sloppctl stop` and keeps the stack. Test `install.sh` in Docker as root (Ubuntu, Fedora; Debian 12 must be refused for its glibc): on NixOS the host's binfmt_misc sends AppImages to `/run/binfmt/…`, which containers lack, so run the script inside `unshare --user --map-users=0:0:65536 --map-groups=0:0:65536 --mount` (needs `uidmap` and `root:0:65536` in `/etc/sub{u,g}id`, and `--security-opt seccomp=unconfined --security-opt apparmor=unconfined`) after `mount -t binfmt_misc none /proc/sys/fs/binfmt_misc`, a private, empty instance.
- Windows builds natively with plain `cargo` and the MSVC toolchain (release builds compile GPUI's shaders with the Windows SDK's `fxc`). `.cargo/config.toml` links the C runtime statically (`+crt-static`), since a fresh Windows has no `VCRUNTIME140.dll`, and the release workflow checks both programs with `dumpbin /dependents`. From Linux, `cargo check --target x86_64-pc-windows-gnu` (with a MinGW gcc as `CC_x86_64_pc_windows_gnu` for `ring`, and MinGW's `windres` on PATH or as `WINDRES` for `build.rs`) type-checks both crates; core's tests and `sloppctl.exe` also run under Wine, the GUI doesn't (no `icuuc.dll`, no GPU). Under Wine `net::tests::sees_our_own_listener` fails (its `GetExtendedTcpTable` gives every socket owner PID 0), and console programs get no `conhost.exe`; CI's Windows runner is the reference.
- Releases: bump `version` in the workspace `Cargo.toml`, then push a matching tag (`git tag v0.2.0 && git push origin v0.2.0`). `.github/workflows/release.yml` builds a Linux x86_64 AppImage and tarball (plain cargo on Ubuntu 24.04, so glibc ≥ 2.39), an Apple silicon dmg and a Windows x86_64 Inno Setup installer and zip, and publishes them as a GitHub release; a tag that doesn't match the version fails the run. "Run workflow" builds without releasing, all platforms or one (`gh workflow run release.yml --ref <branch> -f platforms=windows`).
- Debug builds: `.github/workflows/debug.yml` runs only by hand ("Run workflow", or `gh workflow run debug.yml --ref <branch> -f platforms=linux|macos|windows|all`) and attaches the dev-profile binaries with their debug info (`.dSYM` on macOS, `.pdb` on Windows) to the run for 14 days. It restores CI's check-job cache (read-only, `shared-key: check`), so its build environment must stay the same as CI's.
- CI: `.github/workflows/ci.yml` runs on every branch push (and on pull requests from forks): `fmt --check`, `clippy -D warnings` and the workspace tests on Linux, macOS and Windows, then `crates/slopp-core/tests/servers.rs` against apt's servers (PHP-FPM and mod_php), Homebrew's (Homebrew httpd with mod_php, Apple's httpd with PHP-FPM) and winget's on Windows (the Install button's packages, with `--silent`; Apache Lounge's zip from the manifest's URL into `C:\Apache24` when winget reports its usual stale hash; the job drops the image's own PHP, Apache and MySQL from `PATH`, so SLOPP finds winget's through `winget::program_dirs`). The server tests are `#[ignore]`d so a plain `cargo test` never launches servers; they start Apache, PHP and MariaDB in temporary roots on free ports, print the servers' logs when they fail, and stop everything even then. Inside the Nix shell they find the servers on PATH; outside it, Ubuntu's `apache2 php-fpm php-mysql mariadb-server` (plus `libapache2-mod-php` for mod_php) work too.
- Website: `site/` is a static one-page site (`index.html` with inline CSS/JS, no build), deployed by Vercel (project `slopp`, https://slopp.gs0.me; gs0.me's DNS is on Cloudflare, with a DNS-only CNAME to Vercel): the root `vercel.json` serves `site/` as is, sets its headers, and skips Git deploys for commits that touch none of `site/`, `vercel.json` and `.vercelignore`; `.vercelignore` keeps `vercel deploy` from the repo root to those two. Vercel Web Analytics is on: the page loads `/_vercel/insights/script.js`, which only exists on Vercel (a local preview 404s it, harmlessly). The page is drawn as the panel's own window on a desktop backdrop, so keep it in step with the app's views: a sticky title bar (brand, tabs as section links, the System/Dark/Light appearance as a segmented control), a working demo of the rack (`views/rack.rs`: bezel LEDs, readings, Admin, Start/Stop) feeding a log like `views/console.rs`, beside a mock browser the Admin buttons open (a `mail.php` whose `mail()` lands in a Mailpit inbox, and phpMyAdmin; each page fails as the real one would while its servers are stopped), then settings-style groups (`views/settings.rs`' 220px label column) and a status-bar footer. It reuses the panel's Ayu palette tokens, sizes and IBM Plex (woff2 made from `assets/fonts` with `woff2_compress`); the appearance script in `<head>` sets `data-theme` before first paint, remembered in `localStorage`; light styles key on `[data-theme="light"]`, and the screenshot swaps with it. The intro's big mark (its units toggle the demo, like the tray) and the title bar's small one redraw `tray::icon`'s geometry in SVG with live lamps, as `brand::mark` does, so keep them in step if the mark changes. Download links start at `releases/latest` and the page swaps in the asset URLs from the GitHub API, matched by file-name suffix (`linux-x86_64.AppImage`, `macos-arm64.dmg`, `windows-x86_64-setup.exe`, …), so keep those suffixes stable. `panel-dark.png`/`panel-light.png` are 2160×1440 shots from the headless sway setup below, run in `bwrap` with `/home` a tmpfs and `HOME=/home/user` (bind `~/.cargo` back in: debug builds read gpui-kit's icons from the registry at runtime), with autostart of all three modules on 8080/8443/3306/1025/8025 (`grim` by its full path: the dev shell's `PATH` replaces sway's), then `oxipng -o 4 --strip safe`.
- Try the stack without the GUI: `SLOPP_ROOT=<dir> XDG_CONFIG_HOME=<dir> sloppctl start|stop|status|ports|paths|install-phpmyadmin|install-adminer|install-servers`.

## Running and inspecting the UI

- Don't drive the GUI with xdotool/ydotool or screenshot the user's desktop. Screenshot in a headless sway instead: `nix shell nixpkgs#sway nixpkgs#grim`, a config with `output * resolution 2200x1500 scale 2` and an `exec` that starts `target/debug/slopp`, sleeps, runs `grim`, then `swaymsg exit`; run sway with `WLR_BACKENDS=headless WLR_RENDERER=gles2 WLR_RENDER_DRM_DEVICE=/dev/dri/renderD128` and `DISPLAY` unset.
- Keep test runs off the user's real stack and settings with `SLOPP_ROOT` and `XDG_CONFIG_HOME`.
- Dev hooks: `SLOPP_UPDATE_FROM=<version>` compares releases with that version instead of the build's (to see the update notice and the Updates group with the latest release), `SLOPP_PAGE=ports|settings` opens that page, `SLOPP_THEME=light|dark` overrides the system appearance and the Appearance setting, `SLOPP_HIDDEN=1` starts without a window, `SLOPP_TRAY_ASSUME=1` registers the tray even with no tray host, `SLOPP_LOG=<tracing filter>`. To exercise a start without clicking, put `{"autostart":["mysql"]}` in the test settings.json.
- Test the tray without touching the user's panel: run sway inside `dbus-run-session` with `SLOPP_TRAY_ASSUME=1`, then drive it with `busctl --user`: find `org.kde.StatusNotifierItem-*`, read `ToolTip`/`IconPixmap` on `/StatusNotifierItem`, list the menu with `call -- <name> /MenuBar com.canonical.dbusmenu GetLayout iias 0 -1 0` (the `--` keeps `-1` from being read as an option) and click with `Event isvu <id> clicked s "" 0`. `swaymsg kill` closes the window.
- Only one SLOPP runs per user: a second launch connects to `$XDG_RUNTIME_DIR/slopp-<uid>.sock`, asks the first to show its window and exits. Quit a test instance before starting another.
- Servers started by the panel outlive it by design; stop them with `sloppctl stop` after testing.
- macOS has no headless compositor, so the test instance opens on the real desktop (still with `SLOPP_ROOT`/`XDG_CONFIG_HOME`, and high ports in the test settings.json so it can't collide with a real stack). Capture just its window: find the window number with `CGWindowListCopyWindowInfo` for the pid, then `screencapture -x -o -l<number> out.png`. Drive the menus and the menu bar item through System Events (needs Accessibility permission for the terminal): `osascript -e 'tell application "System Events" to tell process "slopp" to click menu bar item 1 of menu bar 2'` opens the tray menu, then `click menu item "Stop all" of menu 1 of menu bar item 1 of menu bar 2`; `help of menu bar item 1 of menu bar 2` is the tooltip; app menus are on `menu bar 1`. GPUI's own widgets aren't exposed to accessibility.
- In test scripts, never `pkill -f` a pattern that also appears in the script's own command line, and don't start `httpd` as a plain background job of the script's shell: on SIGTERM it signals its whole process group.

## Architecture

- `slopp-core` (no GPUI):
  - `Layout`: every path inside the stack root (XAMPP-like). Unix sockets go to `tmp/` unless the path would exceed the 108-byte socket limit, then to `/tmp/slopp-<uid>-<hash>` (`Layout::sockets`). Never derive it from `$TMPDIR`: the socket path is written into the write-once configs, and `nix develop` changes `$TMPDIR`. The default root and settings live in `~/.local/share` and `~/.config` on macOS too (`layout::base_dir`), not `~/Library/Application Support`: `mariadb-install-db` breaks on the space. On Windows they are `%LOCALAPPDATA%\slopp` and `%APPDATA%\slopp`.
  - `Toolchain::detect`: finds httpd (+ modules dir via `httpd -V`), PHP (prefers `libphp.so` → mod_php + prefork, else PHP-FPM + event), MariaDB and Mailpit on PATH plus sbin dirs (and `/usr/libexec` for `mariadbd`, where Fedora puts it); `Settings.binaries` overrides. On macOS `search_dirs` adds Homebrew/MacPorts prefixes and unlinked Homebrew kegs (`opt/{httpd,php,mariadb}[@version]`) and puts `/usr/sbin` last, so a Dock launch (bare PATH) finds the same programs as a terminal; Apple's `/usr/sbin/httpd` refuses unsigned modules, so it always gets PHP-FPM. On Windows (`windows_dirs`) it adds `C:\Apache24`, Chocolatey's dirs, `C:\php*`, `Program Files\MariaDB *` (newest first) and `C:\xampp`, follows Scoop shims to the real program (`.shim` files), resolves paths with `dunce` (no `\\?\`), and PHP is always mod_php: `php8apache2_4.dll` beside `php.exe` (Thread Safe builds only; there is no PHP-FPM).
  - `setup`: creates dirs; user-facing config files are **write-once** (`write_once`), never regenerated. `php-fpm.conf` in `run/` is internal and rewritten each start, as is `run/php/slopp.ini`. PHP's `mail()` goes to Mailpit: on Unix php.ini's `sendmail_path` runs `run/sendmail` (`setup::write_sendmail`, rewritten on each Apache/Mailpit start: `exec <mailpit> sendmail -S 127.0.0.1:<smtp>`, or a refusal when there's no Mailpit), and `setup::ensure_php_mail` appends that section once to an older php.ini that doesn't mention `sendmail_path`; on Windows `slopp.ini` sets `SMTP`/`smtp_port`, and php.ini's mail section is `sendmail_from` (PHP for Windows refuses a message without a `From:` header otherwise; `ensure_php_mail` adds it there while php.ini doesn't mention `sendmail_from`). Templates that differ on Windows have a `*_for(…, windows)` twin so tests cover both: there phpMyAdmin, Adminer and the client reach MariaDB over TCP on 127.0.0.1, and `php.ini` lists `extension=` lines. `httpd.conf` guards the Unix MPMs and `mod_unixd` with `<IfModule !mpm_winnt_module>`. On Windows `mariadb-install-db.exe` is a different program from the Unix script and only gets `--datadir`, and `my.cnf` holds no paths: MariaDB before 10.11 reads it in the Windows code page, so `Stack::start_mysql` passes datadir, tmpdir, log-error and pid-file as arguments (which Windows converts for the program). Output and logs of servers are read with `process::decode` (UTF-8, else the ANSI code page).
  - Machine-specific values reach Apache as `-C "Define …"`/`-D` flags (`SLOPP_MODULES`, `HTTP_PORT`, `HTTPS_PORT`, `SSL`, `PHP_FPM`/`PHP_FPM_SOCKET`, `PHP_MODULE`/`PHP_MODULE_PATH`) built in `Stack::start_apache`; MariaDB gets `--port`. Mailpit has no config file: `stack::mailpit_args` gives it everything (127.0.0.1 only, `mailpit/mailpit.db`, any SMTP login, `--disable-version-check`); its version comes from `mailpit version --no-release-check` (plain `version` asks GitHub), whose first word is `argv[0]`, not "mailpit". Keep it that way so ports/paths never require rewriting user configs. On Windows mod_php also gets environment: PHP's folder first on `PATH` (its DLLs' dependencies) and `PHP_INI_SCAN_DIR` = `run/php`, whose `slopp.ini` sets `extension_dir`. Elsewhere `Stack::unix_php_env` asks the PHP that runs (the `php` CLI for mod_php, else PHP-FPM itself; `-c` SLOPP's php.ini, `-m` and `-i`) which of `templates::EXTENSIONS` (plus a shared mysqlnd) it has as `.so` in its `extension_dir` but doesn't load (`toolchain::unloaded_extensions`): Arch enables mysqli, pdo_mysql, curl, intl and zip in its own `/etc/php/php.ini`, which SLOPP's replaces. Only then it writes `slopp.ini` with those and passes `PHP_INI_SCAN_DIR=:run/php` (the leading `:` keeps PHP's own scan dir) to Apache or PHP-FPM; otherwise it removes `slopp.ini` and sets nothing, so Debian, Fedora, Homebrew and Nix are untouched.
  - `Stack::start` runs `httpd -t` first so config errors surface with line numbers, then spawns servers in the foreground (`-DFOREGROUND`, `php-fpm --nodaemonize`, `mariadbd`) detached into their own process group (`process::spawn_detached`, which also clears the inherited signal mask and dispositions: GPUI's background threads block SIGTERM on macOS, and a server that inherits that can't be stopped). It records `pid starttime` lines in `run/<module>.pids`; the start time catches reused pids (`/proc/<pid>/stat` on Linux, `proc_pidinfo` on macOS, `GetProcessTimes` on Windows). Windows has no SIGTERM: `process::terminate` sets the servers' own shutdown events (`ap<pid>_shutdown`, what `httpd -k shutdown` sets, and MariaDB's `MySQLShutdown<pid>`), kills at once what has neither, and kills the whole tree (`process::win::tree`) so Apache's worker doesn't keep the ports. Short-lived helpers go through `process::command`, which keeps Windows from flashing a console window; servers get `CREATE_NO_WINDOW` and leave the panel's job object when allowed. `Stack` keeps `Child` handles and reaps them in `status()` so no zombies pile up while the panel runs.
  - `net`: `port_open` (connect probe) and `listeners()` (Linux: parses `/proc/net/tcp{,6}` and maps socket inodes to pids; macOS: `lsof -F`, own processes only. `netstat` prints no TCP sockets when its caller isn't an Apple binary; Windows: `GetExtendedTcpTable`, PID 4 is http.sys, shown as "System").
  - `desktop`: on macOS an editor/terminal setting that isn't a program is an application name for `open -a`; the Shell button hands the terminal app a generated `run/shell.command`, since `open` passes neither environment nor working directory. On Windows files and URLs go to `ShellExecuteW` (Notepad for files with no associated app), commands resolve through `PATHEXT` (`code` is `code.cmd`), and the Shell button runs `cmd /C start "" <terminal>` so the terminal gets its own console.
  - `install`: the rack's Install button (`Controller::install_servers`, `sloppctl install-servers`) installs what `Stack::installable` says is missing (`install::Package`: Apache, PHP, MariaDB, Mailpit) with the system's package manager, through `install::Installer::find`; when there is none it returns `Unavailable` (a log message and a notice) and SLOPP never installs a package manager itself. All backends stream output through `install::run` (lines split on `\r`/`\n`). On Linux Mailpit isn't the distributions': `Installer::Linux` holds the pkexec installer for the rest and a destination for Mailpit, which `mailpit::install` downloads from GitHub's latest release into `Layout::mailpit_bin` (`mailpit/bin/mailpit`, a static binary; sha256 from the API's `digest`, refused without one); `Stack::new` falls back to that copy (`Toolchain::with_mailpit_at`). `install::via`/`Installer::via` word it ("from GitHub"). `brew.rs`, `linux.rs` and `mailpit.rs` compile on every platform so their tests run in all of CI; only `Installer`'s variants are `cfg`-gated.
  - `winget` (Windows): `winget install --exact --source winget` per package: `ApacheLounge.httpd`, `PHP.PHP.<series>` (Thread Safe, the `PHP_SERIES` constant), `MariaDB.Server` and `axllent.mailpit`. No `--silent`: for an MSI that is `/quiet`, which can't ask for elevation; without dialogs MariaDB's MSI registers no service. Apache and PHP are portable packages with `ArchiveBinariesDependOnPath`, so winget puts their folders on the user's `PATH` (no links) and a running panel doesn't see it: `winget::program_dirs` scans `WinGet\Packages` (user and machine) for `toolchain::windows_dirs`, then the controller re-detects with `Stack::reconfigure`. Missing winget is only reported, with a link to App Installer.
  - `brew` (macOS): one `brew install httpd php mariadb mailpit` as the user (no password, no services started); `mariadb@11.8` (keg-only) instead when Homebrew's `mysql` or `percona-server` is installed, since `mariadb` conflicts with them. Missing Homebrew is only reported, with a link to brew.sh.
  - `linux`: `pkexec /bin/sh -c <script>` (plain `sh` when already root), one password prompt, with the family from `/etc/os-release` `ID`/`ID_LIKE`: apt (Debian/Ubuntu: `libapache2-mod-php`, so mod_php), dnf (Fedora/RHEL: `httpd mod_ssl`, PHP-FPM) or pacman (Arch: `php-apache`). Debian starts and enables `apache2` and `mariadb` on install (ports 80 and 3306), so the script disables the units of packages it newly installed. NixOS, image-based systems (`/run/ostree-booted`, SteamOS), unknown distributions and openSUSE (its `httpd` is a wrapper around per-MPM binaries with MPM-specific module dirs and `mod_php8.so`, which `Toolchain` doesn't find yet) get advice instead; so does a missing `pkexec` (the `sudo` command). `pkexec` exits 126 when the prompt is dismissed and 127 when there's no polkit agent. The scripts were checked in containers (Ubuntu 26.04, Debian 13 under systemd, Fedora 44, Arch with mod_php and with PHP-FPM) by running `sloppctl install-servers` as root, then starting the stack as a user and loading a mysqli page and phpMyAdmin; mount `/nix/store` read-only so the dev build of `sloppctl` runs there.
  - `update`: SLOPP updating itself from `releases/latest` (prereleases never; versions compared by semver precedence). `Install::detect` tells how this copy was installed: `$APPIMAGE` (Linux only), `*.app/Contents/MacOS` (not under `AppTranslocation`), `unins000.exe` beside `slopp.exe` (the Inno Setup install), else a writable folder with `sloppctl` beside it (the tarball or the zip); `/nix/store`, debug builds and `target/{debug,release}`, read-only folders and systems without a release build only hear about releases. `Install::install` downloads the asset by the same suffixes as the website, refuses one without a `digest`, then moves a new AppImage over the old (as `install.sh`), copies `SLOPP.app` out of the dmg with `ditto` beside the old and swaps it, or writes new `slopp`/`sloppctl` from the archive (Windows renames the running ones to `*.old`, which `Install::clean_up` removes on a later start). The Windows setup is only downloaded: `Restart` runs it with `/SILENT … /RELAUNCH=1`, and `slopp.iss`'s `[Code]` `Relaunch` check starts the new panel as the original user. The controller (`check_for_update`, `install_update`, `restart_into_update`) checks 5 s after the start and every 24 h while `Settings.check_updates`; restarting releases the instance socket first (`instance::release` runs once, so the old panel can't remove the new one's), spawns through `process::launch` (detached like a server, no output; through `appimage-run` when that started the AppImage) and quits without `stop_on_exit`. The panel shows one notice per release with a button to the Updates group (last on the Settings page, scrolled to).
  - `dbadmin::DbAdmin` (phpMyAdmin, Adminer): the admin tools, downloaded on request and served at `/phpmyadmin/` and `/adminer/`; `Stack::db_admin_url` once installed. `phpmyadmin` downloads the latest release (version.txt → files.phpmyadmin.net zip) plus the pinned, SHA-256-checked `boodark-orange` theme (BooDark 1.2.0's own "orange" is cyan relabelled), keeps an existing `config.inc.php` and adds `ThemeDefault` to it if missing. `adminer` reads the version from adminer.org's `latest-mysql.php` redirect, replaces `adminer/adminer.php` and writes `adminer/index.php` and `adminer/adminer.css` (the panel's palette, light/dark by `prefers-color-scheme`, overriding Adminer's `default.css` and `dark.css`) once. `index.php` subclasses `Adminer\Adminer` (socket credentials, `login()` true, `verifyLoginToken()` false) and posts a permanent login itself whenever there's no `username` or no Adminer cookie, since Adminer refuses password-less logins. Older stacks' `httpd-slopp.conf` gets the `/adminer` alias appended (`Installed::apache_conf_changed`).
- `slopp` (GPUI):
  - `controller::Controller` is an app-level model (reach it with `Controller::global(cx)`), independent of any window: owns `Arc<Stack>`, the log, a poll loop (1.5 s, 0.4 s while busy) that computes status/problems on the background executor, and per-module `Phase` (Idle/Starting{launched}/Stopping/Failed) layered over OS status. `Row::observe` takes in a poll and moves the phase on, returning what's worth logging (`Seen`), which `apply_snapshot` words; an update check's outcome is `controller::checked`. Both are plain functions so the unit tests cover them without a GPUI app; keep new controller logic that way. `changed()` notifies views and pushes a `TrayState` to the tray when it differs. Saving settings replaces the stack via `Stack::reconfigure` (children move over). Window-only feedback goes out as `ControllerEvent::Notify`.
  - `crash.rs`: a panic hook writes the message (and a backtrace) to `crash.log` beside `settings.json`, since the release build on Windows has no console; the next start reports it in the log and renames it to `crash.log.old`. A module whose start passed `START_TIMEOUT` (45 s) is marked failed but turns running when its ports open after all.
  - `panel::Panel` is the window: page, console scroll and the settings form, rendering the controller. View helpers take `(&Controller, &Context<Panel>)`; `panel::on_controller(cx, |c, cx| …)` makes click handlers that act on the controller.
  - `tray.rs`: the menu (`TrayState::menu`: Start/Stop all first, then a toggle per module; each entry has a `MenuIcon`, the module's lamp as a dot from `tray::icon::lamp` or a glyph that is an SF Symbol on macOS and an icon theme name on Linux, where the lamp goes over D-Bus as a PNG from `Pixmap::png`) and the icon, rasterised in code (`tray::icon`: the mark, three units joined into an S by grey links, lamps Apache, MySQL and Mailpit top to bottom; white or dark grey (`#5C6166`) units by `tray::light_panel`, a lit lamp a gradient of its colour over the unit's right side, in shades per ink; `Ink::Template` on macOS while no lamp is lit). `brand::mark` draws the same mark with live lamps in the title bar, from the same colours (`theme::MarkInk`); `assets/linux/org.slopp.Slopp.svg` (also the macOS icon) is the mark with no lamps lit, are shared; Linux shows them with `ksni` on the async-io runtime like GPUI's zbus, macOS (`tray/macos.rs`) as an `NSStatusItem` through `objc2-app-kit` on the main thread. Windows (`tray/windows.rs`) uses `Shell_NotifyIconW` from a hidden window on a thread of its own with its own message loop (states arrive via `WM_APP` posts, so it doesn't rely on GPUI's loop); the icon is a DIB from `Pixmap::bgra`, the menu a `TrackPopupMenuEx` with lamps as premultiplied bitmaps, grey ink (classic menus are light), the icon's ink from the taskbar's own `SystemUsesLightTheme`, re-added on `TaskbarCreated` and removed when the app quits (`Controller::remove_tray`). menu clicks and second launches (`instance.rs`, a Unix socket; on Windows `uds_windows`'s AF_UNIX in the user's temp dir) arrive in `main.rs` as `TrayCommand`s over one channel. Taskbar icons: GPUI's Windows windows load icon resource 1, which `build.rs` embeds (`winresource`) from `assets/windows/slopp.ico`; X11 gets `_NET_WM_ICON` from `WindowOptions.icon` (`main.rs::x11_icon`); Wayland docks only match the app id `org.slopp.Slopp` to a desktop file, so `appimage.rs` writes one (and the icon) into `~/.local/share` when running from an AppImage (`$APPIMAGE`), unless another desktop file already covers it (no `TryExec`: GLib and KDE drop the entry when it isn't executable; `Exec` goes through `appimage-run` when that started it, for NixOS); macOS uses the bundle's `SLOPP.icns`. `main.rs` tracks the window (`PanelWindow`) and quits on window close unless a tray exists and `close_to_tray` is set; GPUI's quit mode is `Explicit` so the app can outlive its window. `menus.rs` (macOS only) sets the menu bar menus and Cmd-W/M/H; other shortcuts are bound as `secondary-…` (Cmd on macOS, Ctrl elsewhere).
  - `views/rack.rs` (module units: LED, ports, PIDs, actions; MySQL's Admin is a menu to open or get each `DbAdmin`), `console.rs` (log), `ports.rs`, `settings.rs` (`SettingsView` emits `SettingsEvent::Save`), `brand.rs` (title bar).
  - `theme.rs`: palette tokens for dark/light (`Palette`), taken from Ayu Dark and Ayu Light (the `ayu` npm package's scheme files; each token's doc names its Ayu key), bundled IBM Plex Sans/Mono, gpui-component restyle. Colour comes from status lamps; Ayu's orange (`accent`, dark text on it via `on_accent`) only for the brand and the Start action. Use tokens, not hard-coded colours. `Settings.appearance` (System/Dark/Light) picks the palette through `panel::wants_light`; the Settings page's Appearance group saves it on click (`SettingsEvent::Appearance`), apart from the form's Save. The tray icon follows the system (`panel::system_light`), not the setting, since it sits on the desktop's panel.

## GPUI gotchas

- `overflow_hidden` doesn't clip to rounded corners: a child that touches a rounded edge must round its own corners.
- Wrap clickable things inside `TitleBar` with `brand::controls()` or KWin's window move swallows the click.
- An app-level action handler that needs the window (`menus::in_active_window`) must `cx.defer`: the action is dispatched from inside that window's update.
- `ScrollHandle::scroll_to_bottom` applies at the next layout, so call it from render (the console follows `Log::revision`).
